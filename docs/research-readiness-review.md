# 更新後レビューと研究データの評価

作成：2026-09-30／確認対象 HEAD `476451f`、contentVersion `2026-10-04`。コード・ローカル検証による評価。実参加者のデータ品質、実機動作、現在の公開環境は未確認。アプリの修正は行っていない。

## 結論

現在のログは、卒業研究として「体験型デジタル詐欺学習ゲームの設計と、単群前後比較による即時判断成績・使用体験の探索的評価」を行う土台になる。収集項目を大量に追加するより、参加者の区分、同意の監査、除外処理、測定の妥当性を固める段階である。ただし、本収集前に下記 R1/R2 を解決し、パイロットで実際の欠損・所要時間・難易度を確認する必要がある。論文としての最終的な要求範囲は指導教員と合意する。

「3Dだから効果がある」「ゲームだけが改善の原因」「長期的な被害防止」「現実情報との矛盾を理解できた」までは現在の設計・ログから証明できない。最新の分析計画はこの限界を適切に認めている。研究目的を説明する他の資料も、この主張の範囲に揃えるとよい。

## 前回から改善された点

- research/free の経路とログ区分が追加され、export は自由プレイを既定除外する。本編のカード収集を残すというユーザー判断に沿った改善。
- 解説中の再読み込み、テストの再開フラグ、非表示時間、保存領域例外、版の混在が考慮された。
- 最終保存の確認表示と再試行、集計の状態管理、タイプの説明が改善された。

自由プレイと研究用ログは別コレクションではなく、同じ sessions 内の playMode と export による論理的な分離である。この方式自体は問題ない。ただし開始ボタンは本人の初回を保証しない。共用端末の priorPlays も本人の参加回数ではないため、スタッフ記録との照合が必要。初回終了までコレクションの攻略情報を見せない運用も維持する。

## 優先する修正・懸念

### R1：パイロットの再プレイが本番扱いになる【本収集前・再現済み】

`store/gameStore.ts` の isTestRun は現在の URL と NODE_ENV から判定する。`app/result/ResultClient.tsx` の onReplay はクエリのない結果ページで reset してタイトルに戻す。production 条件の実ストアで、`?test=1` で true → 結果からの reset 相当で false → 次の開始でも false を確認した。

このままではパイロットを続けて実施すると、2人目以降が研究用 export に混ざり得る。testRun と research/free は別の軸である。担当者が明示的に解除する試験モード、または一連の遷移で試験指定を保持する仕組みが必要。暫定運用は参加者ごとに必ず `?test=1` 付きの開始URLを開き、保存データの testRun を確認すること。

### R2：同意の監査と分析対象の確定が未完成【本収集前・再現済み】

`lib/logger.ts` は consent を保存するが、`analysis/export_firestore.py` の sessions CSV は consent.agreed と実際の consent.timestamp を出していない。t_consent は段階の時刻であり、同意の真偽の代用にはならない。

さらに export の既定除外は主に testRun/free で、分析計画の未完了・同意なし・短時間・版混在・確認済み再参加等を全て適用する分析用スクリプトはない。validator の成功と、研究への採用可否を分ける必要がある。合成入力で consent.agreed=false の研究セッションが CSV 出力・検証ともに通ることを確認した。通常UIから同意なしに保存されると実証したものではなく、監査能力の不足を示す。

推奨：同意フラグと同意日時を export し、元データを保存したまま、sessionId ごとの採否・除外理由を生成する。担当者記録と突合できる匿名の受付番号等を用意し、本人初回、パイロット経験、支援・中断を記録する。個人情報を増やすこと自体が目的ではない。未同意データは研究分析に使わない。

### R3：古い集計通信が次の参加者の状態を変更する【中・ロジック再現済み】

結果画面の集計 Promise 完了時に `useGameStore.getState().setStatsState(...)` が呼ばれ、送信元 sessionId を確認しない。通信待ち中にリプレイすると、新セッションを done/failed に変更できる。実ストアと遅延 Promise で新セッションが done になることを再現した。ブラウザ・Firestore 全体の試験ではない。

送信元 sessionId を捕捉し、現在も同じセッションの場合だけ状態更新する。表示用集計の問題であり、研究用回答が書き換わる問題とは区別する。サーバー側の重複排除を導入しない既決定はそのままでも、この競合は防げる。

### R4：結果ページの直行ガードが phase を変更する【中・静的確認】

`app/result/ResultClient.tsx` は未完了なら /game に戻す一方、独立した effect で transfer_test 等へ setPhase する。描画を null にしても effect は動く。`app/game/GameClient.tsx` は phase=transfer_test なら終了画面を初期表示するため、本編が途中の結果URL直行から誤った終了画面・往復になる可能性がある。

gameDone が成立するまで結果側の段階更新を行わないこと。1〜5問回答時の /result 直行・戻る操作で実機再現を確認する。現時点ではブラウザでの再現済みとはしない。

### R5：アンケートの値域検証が不足【中・合成データで再現済み】

SUS 全項目99、自己効力感99、学習実感99を入れた合成データでも ERROR 0 だった。通常UIは値域を制約するが、収集後の品質チェックとしては不足する。質問ごとの有限な整数1〜5、必須・欠損、mode 等の列挙値を検証する。SUS が計算できることと、妥当な回答であることを区別する。

### R6：反応時間から引く非表示時間の区間が一致しない【中・静的確認】

`store/gameStore.ts` の reactionTimeMs は初回調査から回答まで、hiddenMs はシナリオ開始から回答まで。`lib/playerType.ts:63` の activeRt は後者全体を前者から引いている。初回調査前の非表示40秒、調査後の回答20秒なら、活動時間を0秒扱いし得る。

診断の時間軸や直感派の分類に影響する。引き算するなら初回調査以降の非表示時間を別に測る。現行の研究計画は非表示の多い試行を除外する方式なので、その方針を維持し、研究分析にこの activeRt を流用しない。

## 現在のログで評価できること

| ログ・情報 | 利用できる評価 | 解釈の限界 |
|---|---|---|
| 事前・事後の回答、正誤、問題ID、フォーム割付 | 対応のある正答数変化、見逃し・誤警報、問題別成績 | 各6問なので1問で約16.7ポイント。詐欺/安全別は各3問で約33.3ポイント |
| 確信度 | 誤答時の高確信、正答/誤答別の分布 | 1〜5の順序尺度。正答確率と同一ではない |
| 本編の調査対象・再調査・両対象確認・ヒント | 確認行動の記述、成績との関連 | 開いたことは理解の証拠ではない。ヒント利用者の比較から因果効果は言えない |
| 反応時間、非表示、再開、段階時刻 | 所要時間、操作負担、中断の把握 | 読解、移動、端末差等が混ざる。上記の測定区間にも注意 |
| SUS、自己効力感、学習実感等 | 使用体験・主観評価 | SUS は学習成果ではない。単一項目を検証済み尺度と扱わない |
| mode、testRun、版、完了状態、属性等 | 対象者の選定と記述、欠損・除外の報告 | 同意のCSV出力、本人初回の照合、除外処理を補う必要あり |

主解析の単位は参加者である。30人×12回答を360人相当の標本として扱わない。本編のタイプ・カード・表示用ランキングも研究成果の指標には使わない。

## 研究計画の仕上げ

1. 主要評価は事前・事後の正答数差の一つに固定する。副次評価・探索的評価と分け、有意差が出なかった場合も推定値、区間、限界を報告する。
2. Wilcoxon は6問の離散得点なので同順位と差0が多くなる。検定方法、差0の扱い、全員差0の場合を分析前に指定する。exact と漸近法で同じ Z が得られるとは限らず、計画の r=Z/√N は Z と N の定義を明記するか、定義した順位ベースの効果量に変更する。SciPy の公式説明でも同順位・差0に注意が必要とされる：[wilcoxon](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.wilcoxon.html)。
3. ブートストラップは参加者の事前・事後ペアを一緒に再標本化する。乱数 seed、欠測の扱い、区間の計算法を固定する。N=30 の d≈0.53 という目安を、そのまま Wilcoxon の検出力保証にしない。
4. A→B/B→A の人数と成績を報告する。難易度タグだけではフォーム等価性を保証できない。少人数パイロットで床・天井効果を確認するが、5〜8名だけで尺度の妥当性を確立したとはしない。項目と合計点の相関は、その項目を除いた合計点を使うか明記する。
5. 「矛盾の理解」を主要な主張に残すなら、選んだ通知ID・判断理由、または評価基準を定めた短い聞き取りを追加する価値がある。現在の目的を即時判断成績に絞るなら、まず必須の品質改善を優先し、回答負担を増やさない。
6. 本収集時の問題文、items.json、contentVersion、コードのコミット、分析計画を固定保存する。集計結果を見て有利な除外条件や問題を選び直さない。現行 items.json のみで旧版を判定しない。

論文の結果章は、参加者の採否と欠損 → 対応のある成績変化 → 見逃し/誤警報と確信度 → 確認行動 → 使用体験、の順で構成できる。追加の大規模機能や3D演出より、これらを再現できる分析処理と実機パイロットが優先される。
