## 2. A1：戻る／再入場で本編を進められない

### 原因と影響

- `app/game/GameClient.tsx:61` の初期stageは、`phase === "transfer_test"` のときだけ本編終了画面。それ以外は練習済みなら `main`。
- `app/result/ResultClient.tsx:67` はアンケートで `survey`、結果で `result` にphaseを変える。
- この状態で `/game/` に戻ると `main` になり、部屋と「6 / 6」が表示される。
- 一方、`GameClient.tsx:100` の調査処理は `exploring / investigating` 以外を拒否する。判定・ヒントのボタンも当該phaseでは出ない。結果へ進む出口も表示されない。

想定される通常操作は「本編終了→事後テスト→アンケート、または結果発表→ブラウザで戻る」。自由プレイの結果から戻る場合も `result` なので該当する。ブラウザの進む操作等で復帰できる場合はあるが、画面内では続行方法がない。今回の確認ではログ消失や回答の二重記録までは観測していない。

### 再現の証拠と範囲

公開中のページをEdgeの非表示ブラウザで開き、保存済み状態をページ読み込み前に設定した。`practiceDone=true / currentIndex=5 / logs=6件` とし、phaseだけを変えて比較した。

| phase | `/game/` の表示 |
|---|---|
| `transfer_test` | 本編クリア・事後テストへ進むボタンが表示される |
| `survey` | 部屋・6/6のみ。判定／終了へのボタンがない |
| `result` | 部屋・6/6のみ。判定／終了へのボタンがない |

これは合成の保存状態を用いた再入場確認であり、実機で履歴を一連に操作した通し試験とは区別する。原因は上記ソース分岐でも確認できる。

さらに、`app/pretest/PretestClient.tsx:24` は再訪時も無条件でphaseを `pretest` にし、「ゲーム本編へ」で `practice` にする。本編途中に事前テストへ戻って再入場する場合も、練習済みの `main` と `practice` の不一致が生じる構造。こちらはコード確認で、ブラウザ再現は未実施。

### Claude Codeに依頼する最小修正

1. **回答済みの進捗を優先して遷移先を決める。** 本編終了後に `/game` に入った場合は、回答済みの最終解説を出すべきケースを除き、終了画面または `/result` に誘導する。survey・結果の保存済み内容を維持する。
2. 終了済みの事前テスト等への再訪で、進行済みのphaseを巻き戻さない。本編途中の再開では、未回答の問題・回答済みの解説・練習の状態を区別する。
3. 既存ログ・sessionIdをリセットして解消しない。回答配列を増やすだけの再回答も許さない。

確認条件：本編途中→戻る→進む、最終解説中の再読み込み、事後テスト途中の戻る、アンケート→戻る、研究結果→戻る、自由プレイ結果→戻る。復帰後に回答・ヒント記録・出題順が保持され、本編ログが6件を超えず、事前／事後も各6件を超えないこと。画面を経由する回帰確認が必要で、store単体9件だけではこの不一致を検出できない。

## 3. A2〜A5：公開前に埋める確認事項

### A2 実機の操作

Android ChromeとiOS Safariで、それぞれ研究経路と自由プレイを確認する。横向きへの切替、練習の移動・視点・調査、判定とヒントの同時表示、通知パネル／判定／解説の末尾へのスクロール、縦向きへ戻した後のアンケートを確認する。短い横画面でも「決定する」「次へ」が押せることを確認する。

今回、844×390相当の画面でヒント表示と本編6問の進行は確認できた。ただしマウス相当のDOM操作とソフトウェア描画であり、実際のタッチ操作、Safari、実端末のFPS・発熱・メモリを保証しない。機種情報と問題の起きた場面を残し、性能に問題が出た場合のみ描画負荷を局所的に調整する。

### A3 実際の保存経路

テストモードで研究経路を1回完了し、結果画面の「データ送信済み（サーバーで確認）」を確認。その参加者コードの実ログを `--include-test` でexportし、6件の本編・各6件のテスト・アンケート・版・hintAtScenarioMsを照合する。通信断で結果まで進めたケースは、復帰後の到達と、結果画面を再読み込みした場合の再確認も行う。

エクスポート後は `validate_export.py` → `select_sample.py --include-test --content-version 2026-10-06`（修正で版を変えた場合はその版）→ `analyze_primary.py`。スタッフ記録があれば `--staff` も渡す。意図した再読み込み等のWARNは理由を確認し、ERRORは解消する。

今回Firestoreへの読み書きは実施していない。公開ページの動作確認も非同意の合成状態を使い、Firestore通信をブラウザ側で遮断した。したがって、本番側ルールの反映状態・クォータ・端末へのオフライン保存は未検証。リポジトリ内のルールファイルを読むことと、配備済みのルールが動くことは別。

### A4 試遊と本収集を分ける

公開が試遊のみなら、その対象と用途を明確にしてパイロットとして扱う。本収集も始めるなら、コミット・contentVersion・items.json・分析計画を固定し、本番端末でテストモード解除を確認する。

`research/free` の分離は有効だが、「はじめて遊ぶ」を選んだことは本人初回の証明にならない。`priorPlays` は端末の開始回数であり、共用端末・別ブラウザ・途中でやめた再開始も含む。現行の担当者記録による照合を継続する。無人の一般公開データも研究に含めたい場合は、この照合ができるかを先に決める。自動で全リピートを除外する変更は、共用端末の別人まで除外するため勧めない。

### A5 公開範囲と書き込みルール

`firestore.rules:11` はsessionsへのcreate/updateを無条件に許可する。読み取り禁止は守られているが、書き込み内容の正当性や送信元は保証しない。既存の分析計画では学祭規模で受容する判断が記載されているため、それを勝手に覆す変更はしない。

ただし、不特定多数へ広く告知する場合は前提が変わる。IDを知らなくても任意の新規ドキュメントは作れ、IDを知っていれば更新できる構造。今回不正書き込みの試験はしておらず、被害が発生したという指摘ではない。

少なくとも公開前に利用量の監視方法と異常時の停止手順、研究対象をスタッフ確認済みに限定するかを決める。ルールでの型・サイズ検証は改善候補だが、それだけで所有者確認や大量送信対策は完了しない。認証を追加する場合はオフライン・再開・保存の回帰試験が必要で、締切前に未検証の変更を入れない。

## 5. 公開後の改善案・研究上の懸念

1. **理解・負担の確認を優先する。** ヒントと要点表示は友人の「面倒に感じる人がいるかも」という懸念への妥当な対応。次は対象年齢・知識の異なる少人数に、どこで迷ったか、何を根拠に判断したか、どの画面で疲れたかを聞く。感想1件から年齢差や学習効果を確定しない。
2. **収集可能なものと証明できるものを分ける。** 本編ログはオブジェクトを開いたことを測れるが、複数通知のどれを詐欺と判断したか、比較して理解したか、解説を読んだかは測れない。現行の「即時の判断成績の変化」を中心に論文を構成し、現実被害の防止・長期定着・3D固有の効果まで広げない。
3. **フォーム差・天井効果を報告する。** A/BのS2やF1の違いは残る。各6問なので既有知識の高い人は伸びを捉えにくい可能性がある。まず割付順別の人数・得点、項目別正答率を確認し、現在のデータを見ながら有利な問題だけへ差し替えない。改訂は次の版として扱う。
4. **行動の分析はまだ別途必要。** `analyze_primary.py` はtestsとsessionsを使い、trialsを読み込まない。本編の比較行動、ヒント、調べ直し、RT、学習実感・没入・難しさ等はすべて自動出力済みではない（コードにも別途集計と明記）。必要なログは多くが既にあるため、公開を止めるための改修ではなく、論文作成前の分析課題にする。RTを集計するときはrestarted・非表示時間の既定基準を適用する。
5. **文書の現行仕様への追従。** `docs/project.md` の一次指標は現行の分析計画と異なる。`analysis/README.md`末尾の「統計分析スクリプトは別途整備」は現在の実装と一部不一致。前者は規約どおり更新案としてレビューを受け、後者は実装済み／残りを分ける。公開直前に採点や問題数を変更する理由にはしない。

「初回と自由プレイの分離」「学習カードの維持」「強制閲覧を追加しない」「問題数をいま増やさない」という既決定を維持してよい。今回の確認から、これらを置換する必要は認めなかった。
