# 問題難易度ルーブリック（設計時）＋実証検証

## 位置づけ
本作は「現実情報とデジタル情報の**矛盾**を見抜く」マルチモーダル課題であり、フィッシング**メール**専用の
NIST Phish Scale をそのまま指標にはできない（メール限定・安全問題/誤警報を扱えない・検証済み尺度でない）。
そこで **NIST の2原理（手がかりの数／前提整合）を下敷き**にした独自ルーブリックで設計時に難易度を見積もり、
**信号検出理論(SDT)・古典的テスト理論(CTT: p値/識別力)による実証**で検証・再校正する（二段構え）。

## 設計時ルーブリック（5因子・各 0/1/2、合計0〜10、高いほど難しい）
| 記号 | 因子 | 0（易寄り） | 1 | 2（難寄り） |
|---|---|---|---|---|
| C | 手がかりの少なさ | 手がかり多数 | いくつか | ほぼ1つ |
| M | 文脈による惑わし（詐欺=前提整合／安全=罠の強さ）| 低い | 中 | 高い |
| S | 矛盾/正常性の微妙さ | 露骨 | 中 | 微妙（homoglyph・サブドメイン・日付1日ズレ等）|
| X | 照合負荷（見比べる情報量・モダリティ）| 低 | 中 | 高 |
| K | 必要な専門知識（ドメイン構造理解 等）| 低 | 中 | 高 |

- **M の解釈**：詐欺問題は「前提整合（本当に待っている等、文脈に合うほど難）」。安全問題は「罠の強さ（一見どれだけ不審に見えるか＝正しく“正常”と言う難しさ）」。
- **難易度帯の目安**：合計 **≤3 = easy／4–6 = medium／≥7 = hard**（あくまで目安。境界はSDT/p値で確定）。

### 採点からの結論（設計時）
- ゲーム内6問はルーブリックと**整合**（Safe2 は上限medium＝強い罠と知識要件でhard妥当）。
- **PRE_S1 / POST_S1（決済・利用の定型通知）は罠が弱く明白な正常 → `medium`→`easy` に再タグ**（両方＝並行フォーム維持）。
- **Safe2 / PRE_S2 / POST_S2** は合計6の**medium/hard境界**。強い心理的罠（要バイアス克服）＋ドメイン知識のため設計上は **hard 据え置き**とし、**パイロットの p値/RT で最終確定**する。

## 実証検証（パイロット後・SDT/CTT）
A-3 エクスポート（`analysis/export_firestore.py` の `trials.csv`／`tests.csv`）を入力に、項目ごとに算出：
- **項目困難度 p値（正答率）**：目安 **.2–.8**。.9超＝天井／.1未満＝床の項目は差し替え。
- **反応時間**（`reactionTimeMs`／`decisionLatencyMs`）：長いほど難しい。
- **確信度**（低い＝難しい）と正誤別の校正（Brier 等）。
- **ヒント使用率**（`hintUsed`）。
- **項目識別力**：項目正誤×総得点の点双列相関（低/負は要改善）。
- **SDT 項目別**：詐欺の見逃し率・安全の誤警報率。
- **再校正ルール**：設計難易度と実証（p値/RT）が乖離した項目は難易度タグを改訂、または題材を差し替え。

- 事前・事後（各）：easy2 / medium1 / hard2（並行フォーム一致）
