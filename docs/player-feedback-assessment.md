# 友人のプレイ感想に基づく課題分析

2026-10-01／コード確認対象 HEAD `78a082d`。ユーザー提供の感想1件と、現行の問題・ヒント・表示・研究フローを照合した。参加者のログ、端末、所要時間、プレイした経路は未提供。以下は原因候補の分析であり、ユーザーテストで原因を確定した報告ではない。

## 1. 感想の読み分け

| 発言 | 分かること | まだ分からないこと |
|---|---|---|
| 知識がそれなりにあるので、ほとんど迷わなかった | 本人は判断負担が低かったと感じた | 実際の正答率、新たに学んだ内容、部屋の情報を使ったか |
| 知識がない中年以上の人なら悩みそう | 知識差による難しさを予測した | その層が実際に悩むか。年齢が原因か |
| 面倒だと思う人は多いかも | 継続意欲・負担への懸念 | 本人が面倒だったとは述べていない。どの画面が負担かも不明 |
| 知識を得たり活用するのが好きなら楽しい | 知的関心と楽しさの関連を示唆する | 興味の低い人が継続できないと確定したわけではない |
| 3D空間は普通のクイズより楽しかった | 3D体験を肯定した本人の主観 | 比較実験での3D優位性、学習効果、他の人への一般化 |

中年以上＝IT知識が少ないとは扱わない。研究の主対象は中学生〜大学生で、若年層にも知識や操作経験の差はある。今回の感想だけで対象年齢を変更せず、まず対象内の知識差・関心差を確認する。

## 2. 中心的な課題仮説

**知識がある人には既知のサインだけで解け、知識が少ない人には判断方法をつかむまでの支援が足りない可能性がある。3Dの魅力はあるが、「調べると分かる」「分かったことを使える」という学習体験が両者に十分届いているか未確認。**

問題を全て簡単にする、難しくする、新機能を増やす、という一律の対応ではこの差を解消しにくい。先に「必要な根拠の明示」「支援の到達しやすさ」「表示上の負担」を整える。

## 3. コードから確認できる原因候補

### F1：既有知識だけで答えられ、照合が省略できる【研究目標に関係】

`app/game/GameClient.tsx`では本編で1つ以上調べれば判定に進める。緊急送金・口止め・ウイルス警告からの電話要求等は、知識がある人ならスマホだけでも判断できる。これはバグではないが、目標である現実情報とデジタル情報の比較が正答に必ずしも必要ではない。

ご友人が実際に省略したかは不明。まず「どの情報を根拠に答えたか」を聞き、正答率だけでなく調査ログを確認する。全オブジェクトの強制閲覧は、クリックを増やすだけで理解の証明にならず、今回の負担の懸念を強めるので勧めない。

### F2：見る場所を示しても、見方を知らない人が残る【支援の課題】

`ConfidenceSlider.tsx`のヒントは判定画面にある。探索中に迷っている人は、先に判定画面を開かなければ支援へ到達できない。ヒント自体も「アドレスを見る」「URLの末尾」等で、何を比較するのかが十分でない箇所がある。

特にS4の「URLの末尾」はパスを指すようにも読める。S1には公式ドメインの比較基準がない。知識のある人は補完できても、知らない人には公平な推論材料になりにくい。

最小改善候補：探索画面から既存ヒントを開けるようにする／ヒントの存在を案内する、比較対象と着目点を平易な言葉にする。現行hintAtMsは判定画面起点なので、入口変更時は時刻定義とログを合わせる。二段階ヒントは必要性を確認してから検討し、利用段階も記録する。

### F3：負担は知識不足だけでなく、根拠の不整合からも生じ得る【先に修正】

前レビューで確認したS2の「国内事故が通知本文にない」、S3の「PC契約メモとスマホ警告がつながらない」は未解決。丁寧に考えた人ほど迷う可能性がある。これを難問の価値や参加者の知識不足と解釈しない。

`docs/content-and-update-review.md`の根拠・解説の整合修正を先に行い、その後に実際の難易度を測る。

### F4：移動・記憶・画面の往復が、比較そのもの以外の負担になる【仮説】

本編は毎回4オブジェクトとスマホの複数通知を提示する。調査パネルは1つずつ開いて閉じる構造で、別の情報を見るには往復する。送信元・時刻・URL等はtext-xsで、URLにはbreak-allがある。実機では文字の大きさ、改行位置、スクロールが負担になる可能性がある。

ご友人は3Dを好意的に評価しているため、3D移動を丸ごと外す根拠はない。最初は実機の文字・URL改行・ラベルを点検し、往復が多く困る場合に限って「一度調べた情報を見返す」方法を検討する。後者は探索負担とログの意味を変えるため、いきなり実装しない。

### F5：学びの要点が長文の中に埋もれやすい【表示構造】

`FeedbackCard.tsx`では全解説を一段落で表示し、続けて学習ポイントを示す。正誤にかかわらず学習ポイントがある点は良いが、分からなかった人は長文から判断手順を拾い、既知の人も同じ情報量を受け取る。

最小改善候補：「今回の根拠」「見比べた2つの情報」「次に取る行動」の短い要点を先に示し、詳しい説明も読める構成にする。URLは解説段階で対応部分を視覚的に示す。正解だけ教える短文化や、解説の強制待ち時間は避ける。既存のスキップ可能な次ボタンを不必要に制限しない。

### F6：研究参加の負担と、ゲームの負担が混ざる【要確認】

研究経路は事前6問・本編6問・事後6問に加え、確信度、属性、SUS10項目等がある。自由プレイ経路とは負担が異なる。友人がどちらを遊んだかは不明なので、「本編が長い」「アンケートが面倒」とは断定できない。

また、出題はシャッフルされ、初心者が必ず易問から学べる順序ではない。現行の順序は研究上の判断を含むので、感想1件で易問固定順へ変更しない。先にどの段階・問題で止まるか確認する。

## 5. 次のプレイで確かめること

友人への追加質問は、本人の経験と予測を切り分ける：
- 「面倒そう」と感じたのは移動、読解、比較、回答回数、解説、アンケートのどこか。本人もそう感じたのか、他の人についての予想か。
- 迷わず答えた問題で、部屋のどの情報を使ったか。見なくても分かったか。
- 遊ぶ前に知らなかったこと、解説で納得できなかったことがあったか。
- 3Dの何がよかったか。探索、見た目、情報を発見すること等を自由に答えてもらう。

その後、対象年齢内で事前知識や学習への関心が異なる人に、同じ版・同じ説明で遊んでもらう。中年以上への対象拡大をこの感想から決める必要はない。

| 観察・ログ | 何を確かめるか | 注意 |
|---|---|---|
| 事前正答数＋ITへの自信 | 経験差と負担が関連しそうか | 自信は知識テストではない。6問の成績も粗い指標 |
| 正答・確信度＋調査対象 | 既知のサインだけで解いていないか | 閲覧は理解の証明ではない |
| ヒント利用・調べ直し・聞き取り | ヒントへ到達でき、読後に比較方法が分かったか | 利用率が低いだけでは不要/発見不可を区別できない |
| 段階別時間・中断・スタッフ支援 | 本編/テスト/アンケートのどこに負担があるか | 長時間＝面倒、短時間＝理解とは限らない |
| 誤答理由と解説後の説明 | 誤解が解消し、根拠を言い直せるか | 同じ問題の直後の言い直しは長期定着ではない |

本編6問でヒント利用率や満足度を見ただけでは、関心の低い人にも有効かは確定できない。少人数では群間の有意差より、つまずきの具体例と修正前後の再確認を優先する。採集済みの友人ログを研究データへ採用できるかは、同意・試験区分・初回条件を別途確認する。

## 6. 評価と検証範囲

今回の感想は「ゲームがつまらない」という否定ではない。3D体験は残す価値のある強みとして扱い、知識量に関係なく比較の手順が分かるかを改善の中心に据える。

コードで確認したのはUI配置・文面・判定条件・出題順・ログ項目。友人の実行ログの解析、実機観察、新しい参加者の試験は行っていない。ゲームの実装は変更していないため、build/lint/型チェックは再実行せず、文書差分と参照を確認した。
