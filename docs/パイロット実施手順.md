# パイロット実施手順（形成的評価・5〜8名）

目的：使いにくさ・誤解・所要時間・保存の確実さを確かめ、本実験前に直すべき点を見つける。
**効果や難易度を統計的に確定する目的ではない**（人数が少ないため）。パイロットのデータは本実験の分析に含めない。

## 事前準備
- [ ] URL：`https://eguchi-kd.github.io/senior-thesis-prototype/?test=1` を各端末で一度開く。**テストモードは端末に保存され、解除するまで続く**（タイトルに「🧪 テストモード中」と出ることを確認）。パイロット終了後はタイトルの「テストモードを解除」を押すか `?test=0` を開く（本番用の端末で解除し忘れると本番データがテスト扱いになる）
- [ ] 端末：Android（Chrome）と iOS（Safari）を最低1台ずつ。横向きにできること、画面の自動回転がオンであること
- [ ] 書面の同意書（未成年は保護者の同意書も）
- [ ] 記録用紙（下の「観察記録」）、ストップウォッチ
- [ ] 1人目の前に、スタッフが一度通しでプレイして動作を確認する

> 公開前の実機確認・本収集の開始手順・緊急停止は `docs/公開前チェックリスト.md` を参照。
> 戻る・再入場の回帰確認：`node scripts/check_navigation.cjs <URL>`（Edge ヘッドレス）。

## 当日の流れ（1人あたり 約15分＋聞き取り5分）
1. 書面で同意を取る
2. 端末を渡す前に、スタッフがタイトル画面を開き、**「はじめて遊ぶ」** を押してから渡す（前の人の続きや、コレクション画面を事前に見ることがないように）。以前に遊んだことがある人は「2回目以降（自由プレイ）」を選ぶ（研究用データとは別に記録される）
   - 未成年の参加者には、結果のタイプ診断は6問からの簡易的なお楽しみ要素で、性格や能力の判定ではないことを口頭で補足する
3. 「一人で、相談せずに進めてください。操作で困ったときだけ声をかけてください」と伝える
4. プレイ中はスタッフは口を出さず、観察記録をつける
5. 終了画面の **参加者コード** と **「✓ データ送信済み」** の表示を確認し、記録用紙に書く（送信待ちのままなら通信を確認）
6. 聞き取り（下記）

## 観察記録（1人ずつ）
| 項目 | 記録 |
|---|---|
| 参加者コード／端末（機種・ブラウザ） | |
| 開始・終了時刻（所要時間） | |
| 操作練習でつまずいた点（移動・見回し・タップ） | |
| スタッフに質問したこと・助けた内容 | |
| 画面が見づらい・文字が小さい・スクロールできない等 | |
| 途中で止まった・再読み込みした・アプリを切り替えた | |
| 酔い・疲れの様子 | |
| 終了画面の保存表示（送信済み／送信待ち／失敗） | |

## 聞き取りの質問（プレイ後）
1. ゲーム本編で「詐欺あり」と答えた問題について、**どの通知が詐欺だと思いましたか？ その理由は？**（→ 判定の対象がずれていないかの確認。対象通知や根拠を選ぶUIが必要かどうかの判断材料）
2. 部屋のどの情報（カレンダー・メモ・ポスター）とスマホを見比べましたか？ ダミーの情報で迷いましたか？
3. ヒントは使いましたか？ 使ったあと、調べ直しましたか？ ヒントは分かりやすかったですか？
4. 事前・事後テストで、意味が分からない言葉や問題はありましたか？（例：ホスト名、ドメイン、示談金）
5. 答え合わせを最後にまとめて見るのは、待ち遠しかったですか／気になりすぎましたか？
6. 結果発表（タイプ診断・グラフ・カード集め）は楽しかったですか？ もう一度やりたいと思いましたか？
7. いちばん分かりにくかった・面倒だったところはどこですか？

## パイロット後にやること
1. パイロットは `?test=1` で実施しているので、**必ず `--include-test` を付けて** 抽出する：`python analysis/export_firestore.py --include-test` → `python analysis/validate_export.py <出力フォルダ>`。0件は検証エラーになる。ERROR 0 件を確認し、記録用紙の人数・参加者コードと件数が一致するか照合する
   - 問題を変更した場合は、先に `node analysis/dump_items.mjs` で問題定義（analysis/items.json）を更新してから検証する
   - 終了画面の保存表示は「✓ データ送信済み（サーバーで確認）」になってから次の人に端末を渡す。「送信待ち」のままなら通信を確認する
   - 担当者記録（参加者コード・本人初回か・支援の有無・中断など）を `participantCode, exclude, reason` のCSVにまとめ、`python analysis/select_sample.py <出力フォルダ> --include-test --content-version 2026-10-10 --staff 記録.csv`（版は lib/version.ts の CONTENT_VERSION。複数の版が混ざると指定なしでは停止する） で除外理由に反映 → `python analysis/analyze_primary.py <出力フォルダ>/sample` で主要評価を確認（パイロットのデータは本実験の分析には使わない）
2. 所要時間の中央値を確認し、倫理申請の「約10分」を大きく超える場合は対応を検討する（問題数を減らさずに、説明文の短縮や練習の短縮で調整）
3. 聞き取り1の結果で、別の通知を理由に「詐欺あり」と答えた人が多ければ、「どの通知が詐欺か」を選ばせる仕組みの導入を検討する
4. 修正点を `docs/分析計画.md` と `contentVersion`（lib/version.ts）に反映してから本実験へ
