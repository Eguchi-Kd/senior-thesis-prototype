## 3. B1：戻る操作でヒント・調査履歴が消える

### 実際に通した経路

1. 合成状態で事前テスト終了画面を用意し、画面のボタンから本編へ進む。
2. 練習で移動・視点変更・調査を行い、本番スタート。
3. 本編のヒントを開き、スマートフォンを調査して閉じる。
4. `history.back()`（ブラウザの戻る）で事前テストへ戻る。新しいガードが本編へ自動で送り返す。
5. 同じ問題を調査して判定し、記録されたログを確認する。

Firestore通信は遮断。途中のsessionStorageを直接書き換えて問題を作ったのではなく、初期状態を与えた後は画面操作と履歴操作で再現した。before/afterのsessionIdと`performance.timeOrigin`は一致しており、同じセッション内のページ遷移である。

| フィールド | 戻る前 | 本編へ復帰後 |
|---|---|---|
| `hintUsed` | true | false |
| `hintAtScenarioMs` | 数値 | null |
| `currentInspected` | smartphone | 空配列 |
| `currentInspectEvents` | 1件 | 0件 |
| `scenarioRestarted` | false | false |
| `resumeCount` | 1 | 1（初期状態の読込による値。今回の戻るでは増えない） |

その後の判定ログも `hintUsed=false / restarted=false` となった。最初の再現では、復帰後の調査からのRTだけが2706msとして残った。元の調査時間を含む通常試行とは異なるが、分析側はやり直しとして識別できない。

### 原因

- `app/game/GameClient.tsx:101`付近のeffectは、`stage=main`でマウントされるたびに `markScenarioStart()` を呼ぶ。
- `store/gameStore.ts:332`の処理は、`perScenarioReset()`でヒント・調査・計測の途中状態を無条件に消す。
- `scenarioRestarted=true`を付ける処理はpersistの再読込側にある。今回のようなクライアント内の戻る／再入場では再読込が走らないため、リセットした試行が通常試行として記録される。

新しい復帰処理で操作不能は解消したが、この既存の初期化処理との組み合わせは検証されていなかった。

### 影響と最小修正案

影響：ヒント利用率の過小評価、結果画面の「自力」判定、確認行動・調査回数・RTの誤記録。事前／事後の正答数が必ず壊れるとまでは確認しておらず、今回の再現で回答済みログの消失・二重化はなかった。

推奨は、**新しい問題の開始と、同じ未回答問題への再入場を区別すること**。同一ページ実行環境で同じ問題を再開する場合、既に行ったヒント使用・調査・計測を維持し、表示だけを探索へ復帰する。調査パネルを開いたまま離れた場合の滞在時間の扱いも合わせて決める。

既存の「やり直し」方式へ寄せる場合でも、少なくとも `restarted=true` を残し、既に見たヒントを未使用扱いにしない。セッション全体のresetや、回答済みログの削除で直さない。

### 回帰確認の追加

- ヒント使用→調査→実際の戻る→自動復帰→回答。ヒント履歴を保持し、時間・調査履歴が保持または明示的なやり直しとして記録される。
- 調査パネル中／判定画面中の戻る、2問目以降での同様の操作、解説中の再入場も確認。
- 修正後、既存11件とstore9件も通す。
- `scripts/check_navigation.cjs`は現状、保存状態を入れてページを開く試験が中心であり、実際の同一ページ内の履歴操作とは異なる。件数チェックも`<=6`なので、既存ログの消失や内容変更を検知できない。件数・sessionId・回答内容・ヒント履歴の前後一致も確認する。

## 4. B2：緊急停止からの復旧手順を補う

`firestore.rules.lockdown`の全拒否は停止手段として適切。一方、コメントの「ルールを戻すと再送される分もある」と、現在の復旧手順だけでは、スタッフが「待てば全部保存される」と解釈する余地がある。

通信断と権限拒否は区別する必要がある。Firebase SDKでは`permission-denied`は恒久的な書き込みエラーに分類され、拒否された書き込みをキューから外す。ルールを戻すだけで、その書き込み自体が自動再試行される保証はない。[Firebase公式SDK：エラー分類](https://github.com/firebase/firebase-js-sdk/blob/main/packages/firestore/src/remote/rpc_error.ts)、[恒久エラー時の書き込み処理](https://github.com/firebase/firebase-js-sdk/blob/main/packages/firestore/src/remote/remote_store.ts)。

アプリ側の`saveSnapshot`も失敗時はfalseを返すだけで、自前の再送キューはない。ただし、同じセッションが端末に残っていれば、結果画面の「再送する」等で現在のデータを新しく送信できる。

公開前に追記する最小手順：

1. 緊急停止したら、新規の研究参加者の受付も止める。ゲーム画面が動くことを収集継続の根拠にしない。
2. 保存に失敗した参加者は参加者コードを記録し、「もう一度プレイ」で状態を初期化する前に復旧を待つ。
3. 通常ルールへ戻した後、残っているセッションの結果画面で再送し、サーバー到達表示とexportで照合する。
4. 既に端末状態が失われている場合は復旧できると約束せず、欠損・除外理由を記録する。

この指摘はコードと公式実装に基づく運用評価。本番の停止ルール適用、拒否の実験、DB削除は今回実施していない。

- **教材と支援の効果**：ヒントの入口・解説要点の改善は維持されている。次は対象者に、どこで迷ったか、ヒントで何が分かったか、何を根拠に判断したかを確認する。追加問題や機能で負担を増やすより、現行の完遂率・所要時間・誤読を確かめたい。
- **研究上の主張**：現状は単群の即時判断成績の前後比較が中心。通知ID・理由・解説の閲覧は記録されず、比較理解そのものや長期定着、3Dの優位性の証明にはならない。B1は特に本編の探索的な行動分析へ影響する。
- **分析の残り**：本編の比較行動・ヒント・調べ直し・RT等の集計は引き続き別途必要。ログが正しければ公開後に実装できるので、分析スクリプトの拡充とログ収集バグを同じ優先度にしない。
- **版の固定**：今回、レビュー中にも2件の配信更新があった。最終確認後はコードを固定し、本収集中に更新しない。表示だけの変更をcontentVersionの対象外とする場合も、現在のversion.tsの「UI変更時に上げる」という説明との整合を取り、実験で使用したコミットを必ず記録する。
